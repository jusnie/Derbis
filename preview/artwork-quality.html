Artwork quality — 480p / 720p / 1080p

Song artwork and artist photos, at three quality bands. A cover is only ever fetched once per band, so picking a smaller one makes every cover and every portrait arrive sooner — on a weak connection that is the difference between a screen of artwork and a screen of grey rectangles.

The app already asks the CDNs for a size that suits the view, but it never asks for a cap. A full-screen player therefore requests artwork at up to 1200 px, and on a weak connection that is a 200–400 KB download before a single pixel is on screen — which is the delay you are seeing, and why some artwork never arrives at all.

The fix is one setting with three ceilings. It does not change the layout, and it does not change which images are used: it changes the =w1024-h1024 or 1200x1200bb the app asks the CDN for, so fewer bytes cross the network. The disk cache keeps whatever it already has, and every skin and every screen honours the same cap.

1 — The row, in Settings → Interface

Placed directly under Visual performance, because both answer the same question: how much work should this phone do for a picture.

Medium720 px

Tapping a band updates the sentence above it, so the trade-off is stated rather than implied. The default is Medium: it is a real reduction from today's 1200 px cap, and 720 px is still larger than any cover is drawn at except the full-screen player.

Artist photos are not a second setting. A portrait is an image like any other, so it goes through the same resolver and takes the same ceiling: the artist page header, the artist cards in Explore, the artist rows in Library and the portraits on the Listening Pulse. Song artwork and artist photos always land on the same band — there is nothing to keep in sync.

Pixels requested of the CDN: 100 % — the same cap the full-screen player used before this setting existed.

3 — The cost, measured in pixels and bytes

A JPEG at quality 85 is roughly 0.35 bytes per pixel for photographic artwork, so the download scales with the square of the ceiling. That square is the whole point: dropping 1200 to 720 removes about two-thirds of the bytes, not two-fifths.

4 — What it does not do

  1. It never upscales. The cap only lowers what the screen already asked for — it never raises it. A thumbnail that wants 256 px still asks for 256 under High, and a view that wants 1200 px is the only one that ever notices the difference.
  2. It never changes what is drawn. Layout, crop, corner radius, the Pixel skin, the player deck: all identical. Only the resolution the CDN is asked for moves.
  3. It does not delete the cache. Artwork already on disk keeps its size; new requests use the cap. Clearing the cache is a separate action and is not needed for this to take effect.
  4. It does not touch Canvas. Animated artwork is video and already has its own Canvas quality control. Two different media, two different controls, no overlap.

Honest limit. Apple and Google take an arbitrary size, so the cap lands exactly on 480, 720 or 1080.
